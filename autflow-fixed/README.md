# AutoFlow · 编排器执行可视化原型

对应《第十二组\_Workflow平台技术设计与执行可视化说明书》第 3、4 章与《需求分析与确认报告》FR-01～FR-08，并补充需求生成和运行历史演示能力。
目标是把"需求 → 任务 DAG → 编排器调度 → 执行可视化 → 人工干预 → 历史回看"这条原型主链路跑通并可现场演示。

* 后端：Python 标准库（`http.server` + 线程），**零第三方依赖**
* 前端：原生 HTML/CSS/JS + SVG，**零框架、零 CDN**，离线可用
* 演示执行器：以确定性模拟器代替真实 Agent 调用，时间、产物、故障都可控可复现

\---

## 1\. 启动

**Windows：双击 `start.bat`**（会自己找 Python、自己打开浏览器，黑窗口要一直开着）。

命令行方式：

```bash
python server.py --port 8010
```

然后打开 [http://127.0.0.1:8010](http://127.0.0.1:8010)。
要求 Python 3.9+，无需 `pip install` 任何东西。

> 注意：Windows 自带"应用商店版 python"占位程序，直接敲 `python` 可能弹出应用商店。
> `start.bat` 已优先使用 `py -3` 启动器，其次用 DSH 自带的 Python，最后才回退到 `python`。

### 常见问题

|现象|原因与处理|
|-|-|
|浏览器显示"无法访问此网站"|服务进程没在跑。双击 `start.bat`，**窗口不要关**（关掉窗口等于停止服务）|
|双击 `start.bat` 弹出应用商店|旧的占位 `python` 被优先命中；当前脚本已改为优先 `py -3`|
|提示"端口 8010 已被占用"|已经有一个实例在跑，直接用浏览器打开即可；要重启先 `netstat -ano \| findstr :8010` 找到 PID 再结束|
|页面能开但画布空白|浏览器缓存了旧 `app.js`，Ctrl+F5 强刷|

## 2.0 设计规格 → 任务分解 → 编排（核心链路）

这是本项目的主链路：**输入一份设计规格，产出该产品的开发任务分解与执行编排并可视化**。

点工作流栏的 **设计规格**（或点工作流栏左侧的「规格：…」文字）打开规格面板：

1. **写规格**：填写规格名称、一句话摘要、正文，再加若干**模块**（每个模块有稳定 ID、优先级 P0/P1/P2、目标、若干条验收条款）和若干**全局约束**。规格存在 `data/specs.json`，可多份并存、随时切换；每次保存递增 `revision` 并生成内容哈希。
2. **选流程模板**：面板顶部的「流程模板」下拉直接选这次按哪套流程编排——**标准 SE 流程**（需求 → 分析拆分 → 架构 → 并行实现 → 质量门 → 回归 → 合并 → 高风险时安全评审 → 审批 → 交付）、**敏捷精简流程**（无质量门与评审，适合小步验证）、**企业合规交付流程**（测试计划先行、串行交付、合规评分与复核、合规负责人审批、归档）。下拉下方直接摊开所选模板的阶段说明，不用去翻文档；同一份规格换模板，预览的结构会立刻重画（同一张规格实测：标准 SE 16 节点 / 企业合规 19 节点 / 敏捷精简 12 节点）。
3. **分解预览**：点「分解预览」，PM Agent 按模块拆出 `tasks[]`——每条任务带 ID、标题、角色、依赖、人日、验收标准、逐条规格出处（如 `SP1/M2/acceptance/1`）、规格版本和任务级 `out_schema`；**同时把编排出来的流程图直接画在画布上，覆盖原来的图**（节点全部显示为待运行）。预览走 `POST /api/specs/{id}/preview`，服务器不落库、草稿和已发布版本都不动，所以这一步可以随便点：按钮会变成「取消分解预览」，再点一次、关闭面板、切换规格或直接退出，画布都会回到之前那张图。
4. **分解并编排**：点「就按这个编排」（未预览时是「分解并编排」），把任务清单按**面板里选中的模板**编排成 DAG 并落库为当前草稿，画布立刻显示。任务之间的 `depends_on` 变成边，没有上游依赖的任务挂到流程主干上。
5. **看分解质量**：点画布上的「需求分析与拆分」（PM 节点），右栏直接显示任务状态、验收标准和规格出处；点某个任务节点，右栏「任务信息」显示任务号、规格版本、优先级、预估人日与逐条验收证据；点清单里的行会跳到对应节点。PM 节点的 `prd-v1` 产物同样保留完整 `tasks[]`。

三层数据关系：`设计规格 spec → 任务清单 tasks[] → DAG 定义`，只有最下层是流程图。**任务清单是数据与视图，不是额外的节点**——不做事的东西不该出现在 DAG 里。

分解规则（`decompose_spec`）：**三级结构**——阶段（设计 / 编码 / 测试 / 评审 / 交付）→ 任务 → 子步骤。

* 每个模块固定一条「功能实现」（写明目标文件、技术路线、验收条款）、一条「单元测试与回归」、一条「代码评审」；
* P0 模块或涉及接口/数据模型的模块，前面补一条「方案与接口设计」；
* 整体再加「工程骨架与环境搭建」在头、「集成联调与整体验收」和「交付清单与上线说明」在尾，全局约束并入整体验收的验收清单。

每条任务都带四个必填字段：`what`（做什么，含验收摘要）、`how`（怎么做：用什么实现、写哪个文件、跑什么命令）、
`files`（落点文件）、`steps`（2–4 个子步骤，每步也写明做什么 + 怎么做）。任务清单按阶段分组渲染，
点「展开 N 个子步骤」能看到完整拆分。角色映射：架构师 / 前端 / 后端 / 测试 / 评审，
`test` 与 `review` 类任务分别落到 `tester` / `reviewer` 角色，配了模型时由它们**真的跑测试**。

### 2.0.1 快速生成（一句话需求，兼容入口）

只想用一句话时点 **快速生成**：按关键词命中能力域、套用所选模板生成骨架 DAG，**不经过任务分解**。

1. 服务端把需求展开成 DAG 草稿并**直接落库为当前草稿**（已发布版本不受影响）；
2. 画布立刻显示生成的图，面板里同时给出**生成依据**（识别到的能力域、风险词、骨架说明），便于说明"为什么长这样"；
3. 之后就是常规流程：勾选「编辑画布」调整 → 校验 → 保存草稿 → 发布版本 → 启动运行。

**这是规则生成，不是大模型生成**：同一需求每次结果一致、且一定能通过 `validate_workflow`。接 LLM 时只需替换 `generate_workflow`（同样返回 `definition + trace`），前端与下游流程不用改。

### 2.0.2 流程模板：可定制的那一半

`templates/*.json` 决定**流程形状**，与规格决定的**任务内容**正交：

|模板|形状|适用|
|-|-|-|
|`default` 标准 SE 流程|需求输入 → 分析拆分 → 架构设计 → 按域并行(≤3) → 质量门分支 → 回归/修复 → 合并验证 →（高风险）安全评审 → 上线审批 → 交付，11 阶段|常规项目|
|`lean` 敏捷精简流程|需求输入 → 拆解 → 按域并行(≤2) → 集成自测 → 上线确认 → 完成，6 阶段|小需求试跑|
|`enterprise` 企业合规交付|需求受理 → 拆解分工 → 概要设计 → 测试计划先行 → 按域串行(1) → 集成验证 → 合规评分分支 → 复核/整改 → 评审汇总 → 安全评审 → 合规负责人审批 → 上线确认 → 归档，14 阶段|资金/合规类|

模板里可以改的四样东西：`pipeline`（阶段序列与类型：start / agent / fanout / condition / branch / join / risk_agent / approval / end）、`concurrency_limit`（并发上限）、`domains`（能力域词典与角色）、`risk_words`（风险词）。**加模板就是复制一份 JSON 改 `pipeline`，服务端每次请求重新读文件，不用重启。**

同一个规格换模板，节点数与形状都会变；同一个模板换规格，任务数与依赖关系会变。`tools/demo_matrix.py` 可以把对比表直接跑出来。

## 2.1 画布编辑与版本管理（FR-01）

**编辑画布**（先确认运行状态为"未启动"，否则要先点重置）：

| 操作 | 方式 |
|-|-|
| 移动节点 | 直接拖拽节点，落点坐标写入定义 |
| 建立依赖 | 从节点底部蓝色圆点拖到目标节点，自动生成边并把依赖写进 `deps`；重复边、自连、成环会当场拒绝 |
| 选中 | 点一下节点或连线：节点加蓝色实线描边（右上角浮出 ✎ / × 两个按钮），连线变粗；点空白处或按 `Esc` 取消 |
| 编辑单个节点 | 选中后右栏自动切到「节点详情」的属性表单，改名称 / 类型 / 角色 / 重试上限 / 表达式；或点节点上的 ✎ 直接聚焦名称输入框 |
| 删除 | 点节点上的红色 ×、按 `Delete` / `Backspace`，或用右栏「删除」按钮；删连线同理 |
| 新增节点 | 左栏「添加节点」：任务 / 条件判定 / 人工审批 / 起点 / 终点，插入在视口中央 |
| 改属性 | 右栏表单：名称、类型、角色、重试上限、条件表达式 |
| 保存 | 点「保存草稿」→ 服务端校验 → 通过才落库；不通过时返回 `E-CYCLE`/`E-DANGLING`/分支缺失等错误并高亮节点 |
| 发布 | 点「发布版本」→ 冻结为不可变版本 `vN`，之后运行可指定该版本 |

版本规则：**草稿可反复改，发布后的版本不可变；运行只绑定具体版本**，运行期间改草稿不影响正在跑的流程（`editor_test.py` 有对应断言）。
版本下拉可切到任意已发布版本只读预览，切回"草稿"继续编辑。

破坏性编辑会被拦下，例如删掉条件节点的唯一分支，保存时直接报错——
条件节点必须同时保留 `true` / `false` 两条出边。

### 2.1.1 点开任意节点：看它自己的内容，并且就地改

不需要先勾「编辑画布」——**视图态点任意一个节点**，右栏就是它自己的内容：

* 任务节点：阶段 / 角色 / 优先级 / 预估 / 规格出处 / 执行器，
  以及这条任务的 **做什么**、**怎么做**、**落点文件**、**子步骤**、**验收条款**；
* 任意节点：当前状态、耗时、尝试次数、质量门、执行说明、**产出内容**、执行日志；
* **产出内容**按字段摊开（摘要、产物文件、代码行数、测试 N/M 通过、测试命令、审批决定、验收结果），
  原始 JSON 折叠在下面，需要时再展开；
* 运行状态与产物以运行快照为准，名称与配置以草稿为准——刚改完名字立刻能看到；
* **没跑过的节点不再是一片空白**：执行说明写「还没运行，点启动运行后这里会写它做了什么」，
  产出内容给出"预计产出"（产物协议、执行角色、落点文件、要满足的验收），
  日志说明为什么还没有；被条件分支跳过的节点会在日志里留一行「跳过：条件分支未命中」。

右上角 **「编辑此节点」**（视图态可用，运行中/已发布版本/历史回看会自动禁用并说明原因）
打开的就是这一个节点的表单：名称、类型、角色、重试上限、条件表达式；
任务节点还有任务标题、阶段、优先级、预估、做什么、怎么做、落点文件、子步骤、验收条款。
改完点「保存草稿」——服务端校验通过才落库，画布立即按新内容重画；「完成编辑」回到详情。
不想留就点「删除该节点」（会同时清理连线和任务清单里的对应项）。

全局约束输入框也从 2 行改成 6 行起、可手动拉高、随内容自动长高（上限 320px），
并实时显示「N 条」，长约束不再挤在一条窄缝里。

## 2.2 运行历史（FR-10）

点工作流栏的 **历史**：列出最近 20 次**已结束**的运行（成功 / 失败 / 取消），每条显示状态、
Run ID、版本、开始时间、用时、节点数、事件数、人工操作次数和当时的**需求原文**。

点任意一条即进入**历史回看**：

* 画布切换成那次运行的定义快照与节点状态（成功绿、失败红、跳过灰），时间线换成当时的事件流；
* 顶部深色提示条标注正在回看哪一次，实时推送在这期间**被冻结**，不会被当前状态覆盖；
* 详情面板可查看当时的错误码、尝试记录、产物和人工审批意见；
* 点提示条上的 **返回当前** 恢复实时视图。

归档写在 `data/runs.json`（原子替换，保留最近 20 条，重启后仍在）。
运行在 `SUCCESS / FAILED / CANCELLED` 三个终态时自动归档，同一 Run ID 不会重复入库。

## 2.3 断线与请求失败的提示

| 场景 | 界面表现 | 恢复方式 |
|-|-|-|
| SSE 连接断开 | 顶部红色故障条："实时连接已断开，正在自动重连；期间降级为 1.5s 轮询" | 自动重连；也可点故障条上的「重试」 |
| 接口 5xx / 网络不可达 | 顶部红色故障条显示 HTTP 状态与原因 | 点「重试」重新拉取状态与编辑器数据 |

| 未捕获的异步异常 | 兜底监听 `unhandledrejection`，同样落到故障条 | 同上 |

故障条与「历史回看」提示条都在页面顶部居中，互不遮挡画布操作区。

## 2.4 执行器与运行可靠性（B 任务）

### 可替换 Agent 接口

执行节点统一通过 `Agent.run(node, context) -> AgentResult` 调用，不再写死在引擎里：

* **MockAgent**（默认）：确定性模拟执行器，无需任何外部 API / Key，可复现失败与产物，全流程可离线演示；
* **LLMAgent**（可选）：OpenAI 兼容端点适配器（标准库 `urllib` 实现），配好 `AUTFLOW_LLM_BASE_URL` /
  `AUTFLOW_LLM_API_KEY` / `AUTFLOW_LLM_MODEL` 后可接入模型；工作流运行默认强制使用 `MockAgent`。
  只有显式启用 `AUTFLOW_ENABLE_LOCAL_CODE_EXECUTION=1` 才开放本机真实执行。

`GET /api/agents` 查看已注册执行器与当前生效项。未设置开发开关时，`agent=llm` 配置不会绕过模拟执行限制。
**编排器、门禁、重试、前端流程都不变**。

### 超时 / 错误分类 / 重试 / 取消 / 分支 / 汇聚

* **错误分类**：`E-TIMEOUT`、`E-FORMAT`、`E-COMPILE`、`E-REVIEW`、`E-NETWORK` 为可重试错误，会自动重试；
  `E-AGENT`、`E-INTERRUPT` 为不可重试错误，**不消耗重试次数**，直接转 `WAITING_HUMAN`。
* **超时**：节点超时归入 `E-TIMEOUT`（可重试）；持续超时耗尽 `max_retries` 后转人工，下游阻断。
* **执行不占引擎锁**：`agent.run()` 在线程池里执行，调度线程只做状态迁移。一次慢的模型请求
  不会阻塞 `/api/state`、SSE 和保存草稿；真实耗时超过节点 `timeout` 时由调度侧判定为 `E-TIMEOUT`，
  迟到的结果按执行令牌丢弃，不会把已经超时的节点又改回成功（`agent_async_test.py` 用 2 秒慢端点验证）。
* **重试**：`retry_count` / `attempts` 记录每次尝试与错误码；单次失败自动重试，超限转人工，人工可 `retry` / `skip`。
* **取消**：运行中 `cancel` 立即收敛在途任务，运行进入 `CANCELLED` 并归档历史。
* **分支 / 汇聚**：条件节点按 `true` / `false` 出边选择下游（未命中为 `SKIPPED`）；`join` 策略决定多入边汇聚时机。

### SSE 断线续接

`GET /api/stream` 支持 `Last-Event-ID` 请求头与 `?last_seq=N` 查询参数，断线重连后从断点事件续推，
前端自动重连 + 1.5s 轮询降级兜底，不丢事件。

### 运行中状态与事件落盘 + 重启恢复

活动运行整体原子落盘到 `data/run_state.json`（限频 0.5s），进程崩溃或重启后按以下策略恢复：

1. 已到达终态的节点保持原样（`SUCCESS` / `SKIPPED` / `FAILED` / `CANCELLED` 均不重做）；
2. 崩溃时仍在 `RUNNING`（结果未知）的节点进入 **`UNCERTAIN`（待核对）**，运行进入 **`RECONCILING`（待核对）**，
   **绝不盲目重复执行**；
3. 人工对每个 `UNCERTAIN` 节点 `POST /api/nodes/{id}/confirm`（核定成功，不重复执行）或 `retry` / `skip`；
4. 全部核对完毕后 `POST /api/run/resume` 恢复调度，直至跑完并归档历史。

重启后历史与已完成节点仍可查看；前端顶栏 / 画布 / 详情面板对 `RECONCILING` 与 `UNCERTAIN` 有独立标注。
端到端验证见 `tools/recovery_test.py`。

## 2.6 模型接入与子步骤代码查看

默认工作流始终是**确定性模拟**（运行过程不调用代码执行器、不写文件、不运行生成代码）。
如需 AI 讨论或真实执行，点顶栏 **「⚙ 模型」** 配置模型；模型入口和状态徽标已合并为一个控件：

|字段|说明|
|-|-|
|服务商预设|OpenAI / DeepSeek / Moonshot / 通义 DashScope / Anthropic / 本地 Ollama，选中自动填 Base URL 与模型名|
|Base URL|OpenAI 兼容填到 `/v1`（只填主机名会自动补 `/v1`）；Anthropic 走 `/messages` 协议|
|模型名|如 `deepseek-chat`、`gpt-4o-mini`、`claude-sonnet-4-5`|
|API Key|只存在本机 `data/settings.json`；接口只回掩码（`sk-t…cdef`），前端从不持有明文。**「彻底清除」**会真的把这个字段从磁盘删掉，并写 `ignore_env_key`，重启后不会复活（若密钥来自 `AUTFLOW_LLM_API_KEY`，面板会标 `key_source=env`，清除后同样不再注入）|
|temperature / max_tokens / 超时 / 工具步数|模型请求参数；工具步数用于讨论等带工具的流程|
|启用模型|勾选并保存后，AI 讨论与真实执行走这个端点；查看代码只在“工作区没有落盘文件”时需要模型生成一次，之后读缓存|

模型配置可用状态由服务端判定：**有 base_url + key 且 mode=llm** 才算可用；
`/api/state` 里的 `settings.active` 就是它。工作流运行默认始终是模拟模式，不会在本机创建代码工作区或执行生成的代码。

同一个面板下半部分还有 **「多个 AI 接入」**：可以同时登记多个端点（比如 DeepSeek 写代码、
Qwen 做评审），每个有自己的 Base URL / 模型 / 密钥，互不覆盖。登记后可以：

* 给五个讨论角色分别指派 AI（见 2.8），讨论时不同角色真的走不同模型；
* 给 8 个任务分组分别指派 AI（见 2.9），作为真实执行时的模型选择；
* 在节点详情里给单个节点再指定 AI（优先级：节点 > 分组 > 默认）；
* 每个接入点单独「测试」，用的是**它自己的**端点与密钥。

### 子步骤代码查看（优先读落盘文件，缺失时生成一次并缓存）

在任务详情中点子步骤旁的 **查看代码**，服务端按 `run_id` 定位这次运行：

1. 工作区里已经有这个文件（真实执行写过）→ 原样读出，`source=workspace`，**不调用模型**；
2. 没有文件（模拟运行、还没跑到该步骤）→ 按任务 + 子步骤让当前模型生成一次，
   写到 `data/preview_cache/<run_id>/`，`source=generated`，弹窗会标注“未执行、未参与测试”；
3. 同一子步骤再次点击 → 直接读缓存，`source=cache`，不再调模型。

生成失败（模型返回空内容）会返回 502，并在消息里带上 `finish_reason`，便于判断是不是
`max_tokens` 太小；没配模型则返回 400，提示先到「模型」面板配置。越界路径（`..`、盘符）
一律 400，且不会触发生成。任何情况都**不会写进工作区、不会执行代码**。

运行历史（`/api/runs/{run_id}`）回看时同样可用，读的是那次运行的目录与缓存。
真实代码只出现在显式开启本机执行的运行里：启动服务前设置 `AUTFLOW_ENABLE_LOCAL_CODE_EXECUTION=1`，
`ToolAgent` 才会把代码写进 `data/workspaces/<run_id>/`；日常使用不要设置此变量。

## 2.7 导入设计规格文档

规格面板顶部新增 **导入设计规格**：选 `.md` / `.txt` / `.json` 文件（也可以直接把文件拖到页面上），
或点「粘贴文本」贴入正文，再点「解析并填入表单」。

解析器（`spec_import.py`）认三种常见写法，并把读到了什么如实告诉你：

* **模块划分表**（真实 SDD 最常见）：`| M1 用户模块 | 注册、登录、JWT | M1, M8 |`
  → 模块名、职责、**依赖列**都读出来（编号 M1~M8 原样保留）；
* `## 模块` / `## Modules` 段落下的 `### 名称` → 每个二级标题一个模块；
* 没有模块段落时，任意 `##` / `###` 标题 → 一个模块；
* 再没有标题时，项目符号列表 `- 登录：账号密码 + 短信验证码` → 一个模块。

术语表、表结构字段表这类表格不会被误当成模块：要么表头写着「模块」，要么整列都是 M 编号，
否则整张表跳过。同理，`- F1 用户注册/登录（…）` 这样的**功能点**会按字面重合度挂到最相关的模块，
作为它的验收条款；`**非功能目标：**` 下面的条目、`## 非功能性设计` 里的表格（性能/安全/可靠性/可维护性）、
以及 `范围外（明确不做）` 清单都会进全局约束（"不做"的写成 `不做：xxx`）。

模块划分表的依赖列会一路带到任务里：分解时**被依赖模块的入口任务先做**（加边前查可达性，
成环的边直接丢弃并在 trace 里记账），所以 M8 基础支撑会排在前面、M7 后台管理排在最后，
而不是所有模块平铺。

模块内的验收条款来自 `验收：`/`验收标准` 段、`- [ ]` 复选框和 `AC-01` 之类的编号行；
全局约束来自 `## 约束` / `## 非功能` / `Constraints` 段或 `约束：` 开头的行。
`FR-xx` / `AC-xx` 编号会被统计进 trace。解析完面板底部列出全部 trace 行（例如
「按标题层级拆出 2 个模块」「抽取全局约束 2 条」「检测到表格：当前按标题/列表解析」），
表单可直接改，确认后再「保存规格」——导入不会绕过保存，也不会静默丢内容。
仓库里带了一份真实样例 `tools/fixtures/xianbei-sdd.md`（《闲贝校园》软件设计规格说明书），
`tools/sdd_flow_test.py` 用它跑完整链路：导入 → 存规格 → 分解 → 编排 → 跑完，逐条断言模块/验收/依赖/内容。
如果是本系统导出的 JSON 规格，则按 JSON 结构直接还原（模块、验收、约束、摘要）。

## 2.8 多智能体讨论：规格 → 任务清单 → 工作流

配好模型后，规格面板里多出一块 **多智能体讨论**。这是"模型真正参与规划"的地方：
它读的不是一句话需求，而是你导入/填写的那份规格，然后由五个角色分两轮把它掰开。

|角色|这一轮要回答的问题|
|-|-|
|产品经理|模块怎么切、优先级凭什么、哪条验收最关键、规格哪里含糊|
|架构师|技术方案、接口与数据结构、依赖方向、最大技术风险|
|开发者|每块落哪些文件、关键实现步骤、难点与工作量|
|测试|测试策略、用例矩阵、可自动化的验收方式与测试命令|
|评审|能不能按这个思路交付、别人没提到的 2-3 个风险与遗漏|

第一轮各自出主张（后面的看得到前面的，不是各说各话）；第二轮**评审先质疑**，
架构师逐条回应、产品经理收口成先后顺序与"哪些先不做"。整个过程边跑边显示在面板里，
每条发言带角色、轮次、时间与要点列表。

讨论结束后，主持人只输出**任务清单 JSON**，不输出图。清单进 `normalize_tasks`：

* 缺 `what` / `how` / 子步骤的，按标题与验收条款补齐；
* 依赖只允许引用清单内的 id，指向不存在任务的丢弃、自依赖丢弃、成环的直接断开；
* 非法角色/阶段/优先级回落到合法值，绝对路径与 `..` 的文件落点过滤掉；
* 一条编码任务或测试/评审任务都没有时，按规格补上，保证图能跑。

修了什么都会列在「代码侧修正 N 处」里，不悄悄改。然后点 **「就按这个编排生成工作流」**，
由 `plan_from_tasks` 按任务依赖编排成 DAG、过校验、落成当前草稿——**图仍然由代码生成，
模型只负责"该做哪些事"**。模型乱答（返回的不是 JSON、或清单空）时会明确失败并提示改用
「分解预览」走离线规则分解，不会给出半张图。

**五个角色可以各用各的 AI。** 在「模型 → 多个 AI 接入」里登记两个以上端点，再给角色指派
（产品经理 / 架构师 / 开发者 / 测试 / 评审），讨论时 `_say` 与表决会带上各自的 `ai_id`；
每条发言都标出是哪个 AI 说的（`ai` / `ai_label`），假端点测试里能看到两个不同模型被真实调用。
这样"评审"和"开发者"不是同一个模型自说自话，反驳才有意义；第二轮反对者回应后重新表决，
同意票够数才判 `reached`，否则 `partial` / `blocked`，需要人拍板或继续。

同一份规格的两条路可以对照着用：离线「分解预览」是确定性的、秒出、不花钱；
「多智能体讨论」会真的读正文与约束，产出更贴规格但依赖模型质量、也要花时间与额度。

## 2.9 任务分组（part）：比阶段更细的一层，画布同色归拢

任务除了「阶段」（设计/编码/测试/评审/交付），还多一层 **任务分组 part**，用来把同一类工作
在画布上圈在一起：

|part|默认含义|颜色|
|-|-|-|
|`skeleton`|工程骨架 / 需求分析 / 架构设计|石板灰|
|`data`|数据模型与迁移|天蓝|
|`api`|接口实现|紫|
|`feature`|功能实现（含针对性修复）|绿|
|`test`|测试验证 / 质量门 / 回归|琥珀|
|`review`|代码评审 / 安全合规|红|
|`integrate`|集成联调与整体验收|青|
|`delivery`|上线审批与交付|紫罗兰|

来源有三处，优先级从高到低：模型在任务清单里显式写的 `part` → 按标题关键词细化
（含"数据模型/迁移"归 data，含"接口"归 api）→ 按阶段/类型回落。模板自带的流程节点
（需求输入、质量门、回归、修复、合并验证、安全评审、上线审批、交付）也会被补上分组，
所以画布上**每一段都有色框**，不会只剩中间任务节点有颜色。

画布上同组节点被同一个**同色虚线底框**圈起来（`#partLayer`，在连线与节点下层），
左上角标「分组名 · N 个节点」；节点顶部还有一条 3px 的同色细条。任务清单表里每条任务
也带同色分组标签。节点详情里可以直接改分组（`part`），改完整张图的分组框立即重排。

分组不只是好看：它还是**执行 AI 的默认指派单位**。`part_ais` 里给某个分组指定 AI 后，
该组节点默认由这个 AI 执行；节点自己的 `ai` 优先级更高；都没指定才用全局默认。
`plan_from_tasks` 把 `part` / `part_label` / `ai` 写进节点（`NODE_FIELDS` 里可查），
真实执行时 `Engine._ai_for()` 按这个顺序解析并选择模型；本机真实执行仅在显式开发开关启用时使用 `ToolAgent`。

## 3\. 演示脚本（约 110 秒）

**① 输入设计规格 → 任务分解 → 编排**

点工作流栏的 **设计规格**，选一份规格（内置示例「登录功能设计规格」，或自己新建一份：写模块、每条的验收条款、几行全局约束）。
先点 **分解预览**：下面是 PM Agent 拆出的任务清单——`T1 工程骨架` → 每模块 `方案与接口设计 / 功能实现 / 验收与回归` → `集成联调与整体验收`，
每条都带角色、依赖、人日、规格出处。这一步**只读**，不动画布。
再点 **分解并编排**：同一份任务清单被编排成 DAG，画布立刻出现新草稿；任务之间的 `depends_on` 就是图上的边，没有上游依赖的任务挂在流程主干上。

**② 看分解质量（这一步最能说明"不是又画了一个框"）**

点画布上的 **需求分析与拆分**（PM 节点）→ 右栏出现 **任务清单表**（ID / 任务 / 人日），当前行高亮；
点清单里的某一行 → 画布跳到对应任务节点；点任务节点 → 右栏 **任务信息** 给出 任务号 / 规格出处（`SP1/M2`）/ 优先级 / 预估人日，下面是该任务的 **验收条款**。
即"规格里的验收条款 → 任务的验收标准 → 节点的验收清单"是同一条线，不是三份各写各的。

**③ 换模板，形状就变**

在同一个规格下点开规格面板，用 **分解并编排** 上方的模板下拉框换 `敏捷精简流程` 或 `企业合规交付流程` 再点一次：
同一条任务清单，`default` 23 节点（质量门 + 审批）、`lean` 18 节点（无架构、无门禁）、`enterprise` 26 节点（测试先行 + 合规评分 + 双审批）。
命令行里也能一眼看到对比：

```bash
python tools/demo_matrix.py
```

**④ 跑一次生成的流程**

点 **启动运行**：并行实现节点同时进入运行中 → 质量门判定走分支 → 上线审批停在 `WAITING_HUMAN`；
在右上「节点详情」看到审批节点后填入意见并点 **批准上线**（意见会记入历史）→ 交付完成、运行成功。

**⑤ 回看历史**

点 **历史**：刚才那次运行已在列表里（状态、版本、用时、需求原文）。点进去回看画布与事件流，
顶部提示条标明"正在回看 RUN-… "，点 **返回当前** 回到实时视图。

> 想回到旧的一句话流程：点 **快速生成**，粘贴"做一个内部管理后台：支持账号密码登录和短信验证码，订单支付结算，报表统计导出"，
> 点 **生成工作流**——按关键词命中能力域直接铺骨架，跳过了任务分解这一层。

**④ 默认 10 节点流程（原始演示）**

演示流程固定为 10 个节点：
`需求输入 → 架构设计 →（登录实现 ∥ 安全扫描）→ 质量门判定 → 回归测试 / 重构 → 合并验证 → 上线审批 → 交付完成`

点击 **启动运行**，依次观察：

1. N3、N4 **同时进入运行中** —— 并发派发（FR-03），左侧"运行中"计数为 2；
2. N3 首次被 **格式门** 拦截 → 状态回到就绪 → **自动重试** → 第二次通过，节点右上出现 `×1` 角标（3.2 重试、3.4 质量门）；
3. N5 质量门判定 `qa\_score=72`，命中 **FALSE 分支**：N6 变为 **跳过**（虚线灰），N7 开始执行（3.3 条件分支）；
4. N8 在 `join=any` 策略下 **汇聚**就绪并完成（3.3 汇聚）；
5. N9 **上线审批**：画布顶部弹出审批横幅，流程整体进入 `WAITING\_HUMAN`（4.3 Human-in-the-loop）；
6. 点 **批准上线** → N10 完成 → 运行成功；右栏时间线记录全部 `PENDING→READY→RUNNING→SUCCESS` 迁移。

**⑤ 异常路径 · 重试上限与转人工**

勾选 **注入故障** 后启动运行：N3 编译门连续失败，`1 次执行 + 3 次重试` 耗尽后转为 **待人工**，
运行整体挂起，下游 N5/N6/N7 全部变 **阻断**（FR-07）。
取消勾选"注入故障"→ 点横幅上的 **修正后重试** → N3 成功、下游自动解阻、流程继续到审批完成。

**⑥ 其它可现场操作的开关**

* **演示模式** 取消勾选 = 顺利路径：全部节点一次通过，N5 命中 TRUE 分支，N7 被跳过；
* **暂停 / 继续**：暂停后不再派发新任务，在途任务继续收敛（3.2）；
* **校验 DAG**：先用当前图跑一次正向校验，再自动用一个"注入环依赖"的负例验证拦截能力，
提示中会给出 `E-CYCLE`（FR-02）；接口还覆盖悬空依赖 `E-DANGLING`、deps/edges 不一致 `E-INCONSISTENT`、重复边 `E-DUP-EDGE`；
* 右栏切换 **事件时间线** 可回看每一步的状态迁移与门禁结论（FR-08）。

## 4\. 状态机与质量门

节点状态：`PENDING → READY → RUNNING → SUCCESS / FAILED / WAITING\_HUMAN`，
分支未命中为 `SKIPPED`，上游未成功为 `BLOCKED`，人工取消为 `CANCELLED`，
崩溃恢复后执行状态不确定的节点为 `UNCERTAIN`（待核对）。
运行状态：`IDLE / RUNNING / PAUSED / WAITING\_HUMAN / SUCCESS / FAILED / CANCELLED`，
重启恢复后的核对期为 `RECONCILING`（待核对）。

质量门：**格式门**（输出 schema）→ **编译门**（语法/依赖）→ **评审门**（评分阈值）→ **人工门**（签署）。
规则是"执行成功 **且** 门禁通过才算 SUCCESS"，门禁结果落在节点的 `gate` 字段，可在详情面板逐项看到。
任一必过门失败：未超重试上限则带反馈重试，超限则 `WAITING\_HUMAN` 并阻断下游——不存在"强行成功"的旁路。

## 5.1 本阶段范围与集成基线（A / B / C 任务共用）

本节作为当前原型的范围、模块边界和联调约定。它描述**当前代码实际采用的方案**，不表示正式生产服务已完成。

### 范围约定

本阶段交付目标是单机、单工作流的可演示原型，闭环为：

`输入需求 → 生成规则化 DAG 草稿 → 人工编辑/校验 → 发布或启动 → 模拟调度与门禁 → 审批/重试 → 终态历史回看`

需求生成当前使用领域词典和固定骨架；Agent 节点默认使用确定性模拟执行器，完成这条原型闭环**不依赖外部模型 API 或 API Key**。接入真实模型通过独立 `Agent` 适配接口完成（已内置可选的 `LLMAgent`，见 2.4），不改变前端与编排器之间的工作流契约。

当前明确不纳入本阶段验收：MySQL 迁移、用户认证与复杂权限、多租户、分布式调度、任意代码执行。它们属于后续扩展或生产化工作，不应被描述为当前已实现能力。真实模型调用为**可选适配**（默认关闭、不依赖外部 API）；运行中断后的自动恢复已在本阶段实现（崩溃后进入可见的核对状态，见 2.4）。

### 模块职责与接口边界

| 模块 | 当前实现位置 | 输入 / 输出边界 |
|---|---|---|

### 工作流与运行契约

工作流定义使用 JSON，核心字段如下：

```json
{
  "workflow_id": "wf_example",
  "name": "示例工作流",
  "version": "v1",
  "requirement": "需求原文",
  "concurrency_limit": 3,
  "nodes": [
    {
      "id": "N1",
      "type": "agent",
      "name": "任务名称",
      "role": "coder",
      "deps": [],
      "max_retries": 2,
      "out_schema": "code-result-v1"
    }
  ],
  "edges": []
}
```

节点类型为 `start`、`agent`、`condition`、`approval`、`end`；按需可带 `expression`、`branch`、`join`、`timeout`、`pos` 等字段。每条边用 `source`、`target` 表示，条件分支边可用 `label: "true"` / `"false"`。`deps` 必须与入边一致；服务端在保存、生成和启动前校验引用、重复边、分支和环依赖。

节点状态统一使用 `PENDING`、`READY`、`RUNNING`、`SUCCESS`、`FAILED`、`BLOCKED`、`WAITING_HUMAN`、`SKIPPED`、`CANCELLED`、`UNCERTAIN`；运行状态使用 `IDLE`、`RUNNING`、`PAUSED`、`WAITING_HUMAN`、`SUCCESS`、`FAILED`、`CANCELLED`、`RECONCILING`。前端文案可以本地化，但不能改变状态含义。每次运行绑定启动时的工作流定义快照，之后编辑草稿不得改写该次运行。

### 联调约定

1. 前端生成需求时调用 `POST /api/workflows/generate`；成功响应中的 `draft.definition` 是画布后续编辑和运行的唯一工作流数据来源。
2. 保存前端编辑结果使用 `PUT /api/workflows/{id}`；发布使用 `POST /api/workflows/{id}/publish`；启动使用 `POST /api/workflows/{id}/runs` 或兼容接口 `POST /api/run/start`。
3. 前端通过 `GET /api/state` 获取快照、通过 `GET /api/stream` 接收 SSE 更新；SSE 不可用时使用轮询。审批、重试、跳过和取消均调用服务端操作接口，并以之后返回的快照更新画面。
4. 历史列表和详情分别使用 `GET /api/runs`、`GET /api/runs/{run_id}`。历史视图只读，不应把历史数据提交回当前草稿或运行。
5. 当前 API 使用标准库 HTTP 和 JSON；成功响应通常包含 `ok`，业务错误包含 `ok: false`、`message`，校验错误另含 `errors`。后续模块不得假设当前已实现统一请求 ID、幂等键或数据库事务。

### 集成验收门槛

- **生成与建图：** 有效需求生成可编辑草稿；生成图通过服务端 DAG 校验；空需求、过短需求和运行中生成均明确拒绝。
- **编辑与版本：** 编辑、保存、发布成功；非法图不落库；运行使用冻结版本，草稿变化不影响在跑定义。
- **执行与干预：** 就绪节点按并发限制执行；门禁失败、分支、重试耗尽、审批、暂停/恢复和取消结果与服务端状态一致；超时与错误分类按 2.4 规则重试或转人工。
- **可视化与历史：** SSE 更新画布和时间线；断线能降级并提示（支持 `Last-Event-ID` 续接）；终态运行可在历史中查看当时定义、节点、事件和需求文本。
- **运行可靠性：** 活动运行限频落盘；重启后在途节点进入可见的 `UNCERTAIN` 核对状态、不盲目重复执行，核对后可恢复跑完并归档。
- **可复现性：** 默认演示不要求网络模型服务或密钥；`acceptance_runner.py` 为每个套件隔离数据与端口，自动记录测试命令、环境版本、日志、截图和结果。

测试注意：不要用“清理测试数据”为由直接删除唯一的 `data/*.json`。统一入口会自动创建并清理临时
数据目录；直接运行单个接口脚本时，才需要自行提供独立实例或备份。`tools/check_ui.py` 已改为相对
自身文件定位项目根目录，可在 Windows、macOS 和 Linux 从任意当前目录执行。

## 6\. 实现取舍与已知限制

* **为什么用模拟执行器**：现场演示需要可复现的失败点（格式错误、评分 72）。执行节点统一走
`Agent.run(node, context)` 抽象接口，默认 `MockAgent`，换 `LLMAgent`（可选）即可接入真实模型，产物 schema、超时、重试策略都不用改。
* **状态只由服务端产生**：前端仅渲染快照/补丁，不自行推演，避免"界面显示成功但服务端还在跑"。
* **SSE 推完整节点集**：单次运行 10 个节点，数据量很小，用"快照 + 增量事件"换取前端零状态合并逻辑；
支持 `Last-Event-ID` / `?last_seq=N` 断线续接，断线后 1.5s 轮询兜底。
* **需求生成是规则而非模型**：`generate_workflow` 用领域词典 + 固定骨架，保证可复现、必然通过校验；
  它不是"理解需求"，需求里没命中的部分会落到通用实现节点。接 LLM 时替换该函数即可，返回结构不变。
* **运行历史只存终态 + 活动运行整体落盘**：归档发生在 `SUCCESS / FAILED / CANCELLED`，最多 20 条，
  含定义快照 + 节点 + 事件；活动运行同时限频落盘到 `data/run_state.json`，重启后把在途节点转为
  `UNCERTAIN` 进入 `RECONCILING` 核对（不盲目重复执行）。事件流为**运行期快照级**回放，非逐 tick 精确重放。
* **未实现**：多工作流并存（目前一个仓库实例只有一条主工作流，生成会覆盖草稿）、
  多租户与鉴权、条件表达式的通用求值（目前只支持 `qa_score >= 80` 这类受限比较）、
  历史记录的删除与分页。真实模型接入为可选适配（`LLMAgent`），默认不启用。
* **编辑布局的取舍**：节点坐标存在定义里（`pos`），进入编辑态时把自动分层结果冻结成坐标；
否则每次加节点都会重排，拖拽就没有意义了。
* **任务分解是规则而非模型**：`PMAgent` 当前使用确定性的 `decompose_spec` 按"模块 → 设计/实现/验收"拆任务，
角色靠关键词启发式判断（模块名写「页面 / 交互」才判成前端），不会真的读代码估工作量。
它是可复现的 Mock 实现；`tasks[]` 已带 `depends_on` / `acceptance` / `acceptance_sources` /
`spec_ref` / `spec_revision` / `out_schema`，后续可替换为真实 PM Agent 而不改变下游契约。
* **规格只能手编**：没有"粘贴一份 Markdown 自动切成模块"的解析器；期望是规格由人或上游工具产出，本项目负责下游。
* **一个实例一条主工作流**：规格可以有多份，但「分解并编排」总是覆盖当前草稿（已发布版本不受影响）。
